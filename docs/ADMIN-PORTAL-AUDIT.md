## Audit event wiring detail (Task G)

- **Pattern used:** reuse each service's existing transactional-outbox dispatch (`outboxEvents: [...]` passed into the same repository call that persists the state change), appending one more `AUDIT_RECORDED` envelope alongside the existing domain event. No new infra required.
- **order-service:** `confirmOrder` → `order.confirmed`; `cancelOrder` → `order.cancelled`. Payload: `action, actorId, actorRoles, resourceType: 'order', orderId[, reason]`.
- **payment-service:** `markCodCollected` → `payment.cod_collected`; `createRefund` → `payment.refund_created`. Payload: `action, actorId, actorRoles, resourceType: 'payment', resourceId, orderId[, amount]`.
- **reporting-service:** already consumes `EventTypes.AUDIT_RECORDED` (`event-consumer.ts` `CONSUMED_EVENT_TYPES`) and projects via `extractAuditData` (`event-handlers.ts`) into `AuditLogProjection`, idempotent by `sourceEventId`. No reporting-side changes were needed — the payload shape emitted above matches `extractAuditData`'s expected keys exactly.
- **catalog-service / media-service — known limitation:** both still call an in-memory `writeAudit`/`recordAudit` helper (array, no RabbitMQ publish). Wiring these into the outbox would require adding outbox/broker dispatch infra that doesn't exist yet for these two services — out of scope for this pass to avoid destabilizing catalog/media. Tracked as remaining work below.
- **Security logging-gap scenarios untouched:** `shouldEmitSecurityAudit` in `libs/shared/security-lab` still intentionally returns `false` (SC-64). That function governs _security_ audit (auth/session events) and is a separate code path from the _operational_ `AUDIT_RECORDED` business events wired here — no conflict.
